## Purpose and scope

Filename Cleanup Preview is a small command-line utility for people who want to normalize filenames in one folder without accidentally overwriting or silently changing files. It first presents a complete rename plan and changes filenames only when the user explicitly requests apply mode.

## Filename cleanup contract

The following cleanup policy is recommended and remains proposed until approved:

1. Preserve the final filename extension exactly, including its case. For names with multiple suffixes, only the final suffix is treated as the extension.
2. Normalize the stem by:
   - trimming leading and trailing whitespace;
   - replacing each run of whitespace, underscores, or hyphens with one hyphen;
   - removing leading or trailing hyphens;
   - converting letters to lowercase.
3. Leave a file unchanged when the resulting name equals its current name.
4. Reject a candidate when cleanup would produce an empty stem, `.` or `..`, a path separator, or an invalid single filename.
5. Do not change file contents, metadata intentionally, or parent directories.

Examples under the proposed policy:

| Original | Proposed result |
| --- | --- |
| `Quarterly Report.PDF` | `quarterly-report.PDF` |
| ` project__notes .txt` | `project-notes.txt` |
| `already-clean.csv` | unchanged |

Operating-system-specific filename restrictions beyond Python and filesystem validation are not broadened into a cross-platform compatibility guarantee for the first version.

## Safety and recovery

Plan validation is all-or-nothing: known conflicts prevent the apply phase from starting. This avoids predictable partial changes.

Unexpected operating-system or concurrent filesystem failures can still occur during application. The implementation should:

- stage affected files through unique temporary names within the same folder;
- record completed operations in memory;
- attempt best-effort restoration when a later operation fails and restoration would not overwrite anything;
- stop rather than overwrite when safe restoration is impossible;
- report the actual final paths and provide clear manual recovery information.

The first version does not promise transactional filesystem behavior or durable crash recovery. A process interruption may leave reserved temporary names behind; those names must be recognizable and reported as conflicts on a later run rather than silently reused or deleted.

The implementation should use a few explicit responsibility boundaries inside the module:

- **Cleanup function:** converts one filename to its proposed filename without touching the filesystem.
- **Planner:** reads one directory snapshot and returns ordered candidate, unchanged, and skipped records.
- **Validator:** rejects invalid, duplicate, occupied, or unsafe destinations before application.
- **Applier:** performs guarded staging and final renames while producing an accurate operation report.
- **CLI adapter:** parses arguments, renders the plan, selects preview or apply mode, and maps outcomes to exit codes.

`argparse`, `pathlib`/`os`, `uuid` or `secrets` for unique temporary names, and `unittest` are suitable standard-library tools. Exact commands belong in `README.md` when implementation begins; no application or runnable commands have yet been created or verified.

## Decisions and uncertainty

### Accepted constraints

- The product is a small Python standard-library utility.
- It operates on one folder.
- Preview precedes any explicitly requested apply operation.
- Existing files must never be overwritten.
- There is no interface beyond the CLI, server, database, external service, or tracker.
- This bootstrap prepares documents only; it does not implement the program.

### Proposed decisions awaiting owner approval

- Process only immediate regular files and never follow symlinks.
- Use the cleanup policy documented above.
- Preserve the final extension’s spelling and case while lowercasing the stem.
- Treat any known collision as invalidating the entire plan.
- Support swaps and rename chains through same-folder temporary names.
- Provide best-effort restoration and an exact recovery report rather than claiming full transactionality.

The cleanup policy is the only material product decision needed before implementation planning. If a different convention is desired—such as preserving stem case, replacing spaces without collapsing underscores, or handling multiple suffixes as a unit—REQ-002 through REQ-008 remain applicable, but transformation examples and tests must be revised first.

### Material risks

- **Case sensitivity varies by filesystem.** Validation must conservatively detect names that may collide on the active filesystem; cross-platform behavior must be tested rather than assumed.
- **The directory can change between preview and apply.** Apply mode must build and validate a fresh plan for that invocation and recheck paths during execution. A previous preview is informative, not authorization for or a guarantee about a later apply.
- **Interruption can prevent complete restoration.** Temporary naming and accurate recovery output reduce harm, but durable crash-safe transactions are outside the first version.
