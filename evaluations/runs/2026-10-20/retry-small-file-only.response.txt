## 1. Purpose and direction

People sometimes need to make filenames more consistent but should not have to trust a bulk rename operation without seeing its exact effects first. Existing shell commands can be difficult to inspect, may behave differently across platforms, and can accidentally replace files when conflicts are overlooked.

The utility will:

1. inspect one explicitly selected folder without recursion;
2. calculate a deterministic cleanup plan for regular files;
3. display the proposed source and destination names without changing the folder; and
4. perform those same changes only after a separate, explicit apply command.

The utility is intended for a person working locally from a command line. It is not a service, graphical interface, file organizer, or general-purpose batch-processing framework.

### Principles

- Preview is the safe default and never changes the filesystem.
- Apply must be explicit; confirmation is never inferred from having run preview.
- Existing paths are preserved. A cleanup operation must not overwrite or replace one.
- Ambiguity blocks mutation rather than being resolved silently.
- Output must make planned, skipped, conflicting, successful, and failed items distinguishable.
- The first version remains small, local, dependency-free, and understandable.

## 2. Outcome and success

### Intended outcome

A user can review an exact filename cleanup plan for one folder and apply it with confidence that unrelated entries and existing destination paths will not be overwritten.

### Observable success measures

- Preview reports every proposed rename and performs no writes.
- Apply requires an explicit apply mode or command.
- Given unchanged input, preview and apply derive the same plan.
- A destination conflict prevents that rename from being attempted.
- Regular files not selected for renaming remain unchanged.
- Directories, symbolic links, and nested contents remain unchanged.
- The process returns a non-zero exit status for invalid input, conflicts that prevent a requested apply, or operational failures.
- Automated tests cover cleanup rules, preview safety, collisions, repeated execution, and apply failures.

No usage-volume, performance, or adoption target has been approved. For this bounded local utility, correctness and preservation of files are the primary success criteria.

## 4. Filename cleanup policy

The user has not yet approved the exact cleanup transformation. The recommended first-version policy is:

1. Operate on the filename only, never its parent path.
2. Treat the final suffix as the extension and preserve it exactly.
3. For ordinary filenames, trim leading and trailing Unicode whitespace from the stem.
4. Replace each remaining run of one or more Unicode whitespace characters in the stem with one ASCII hyphen (`-`).
5. Preserve case and every other character exactly.
6. Leave a name unchanged when the transformation produces the original name.
7. Reject a proposed result whose stem becomes empty.
8. Treat dotfiles with no additional suffix, such as `.env`, as extensionless names and leave their leading dot intact.
9. Do not normalize Unicode, change capitalization, transliterate characters, remove punctuation, or alter extensions.

Examples under the proposed policy:

| Source | Proposed result |
| --- | --- |
| `Quarterly Report.pdf` | `Quarterly-Report.pdf` |
| ` notes  draft .txt` | `notes-draft.txt` |
| `photo.JPG` | unchanged |
| `.env` | unchanged |

This policy is a proposal, not an accepted requirement. Implementation should not begin until the owner accepts it or supplies a replacement rule.

## 5. Workflow

### FLOW-001 — Preview cleanup

- **Actor and purpose:** A local user wants to inspect possible filename changes safely.
- **Entry:** The user invokes the utility with one folder path and no apply option.
- **Minimum input:** An existing, accessible directory.
- **Sequence:**
  1. Resolve and validate the supplied folder.
  2. inspect only its immediate entries;
  3. select regular files while excluding directories and symbolic links;
  4. calculate proposed names using the accepted cleanup policy;
  5. classify unchanged names, invalid results, duplicate proposed destinations, and destinations that already exist; and
  6. print the complete plan and summary.
- **Result:** No filesystem entry is changed.
- **Failure behavior:** Invalid or inaccessible folders produce a clear error and non-zero exit status. Per-file inspection problems are reported and cause the plan to be unsafe to apply.
- **Recovery:** Correct the folder, permissions, filename, or policy issue and run preview again.

### FLOW-002 — Apply cleanup

- **Actor and purpose:** A local user has chosen to perform the calculated cleanup.
- **Entry:** The user invokes the separate explicit apply mode for one folder.
- **Sequence:**
  1. Recalculate the current plan from the live folder; a previous preview is informative but is not reused as stale authority.
  2. Run all validation and conflict checks.
  3. If any blocking conflict or inspection error exists, perform no renames.
  4. For each valid planned change, create the destination without replacement semantics and remove the source only after destination creation succeeds.
  5. Report every success and failure, followed by a summary.
- **Result:** Successfully processed files have their proposed names; all unrelated entries remain unchanged.
- **Failure behavior:** A destination that appears during apply must cause that item to fail without replacing the destination. Because ordinary filesystems do not provide a portable multi-file transaction, an operational failure can leave earlier items completed and later items untouched.
- **Recovery:** The report identifies completed and uncompleted changes. Running preview again derives a plan from the current folder state, making retry safe for remaining work.

## 6. Requirements

### REQ-001 — Inspect one folder without recursion

- **Status/source:** Accepted from the user request.
- The utility must require one folder path.
- It must inspect only entries directly contained in that folder.
- It must consider regular files only.
- It must not rename directories, symbolic links, or anything below a nested directory.
- Missing, non-directory, or inaccessible input must result in a clear error and non-zero exit status.

**Acceptance criteria**

1. A nested file is never included in the plan.
2. A directory or symbolic link in the selected folder is reported as skipped or omitted according to documented output behavior and is never changed.
3. An invalid folder causes no mutation.

### REQ-002 — Produce a deterministic cleanup plan

- **Status/source:** Cleanup is accepted in principle; the exact transformation in Section 4 is proposed.
- Applying the accepted cleanup policy to the same folder state must produce the same source-to-destination mappings.
- Plan ordering must be stable, using filename ordering documented by the implementation.
- A source must appear at most once.
- An unchanged filename must not be treated as a rename.
- An empty or otherwise invalid destination filename must be a blocking validation error.

**Acceptance criteria**

1. Repeated previews of an unchanged folder have the same planned mappings and order.
2. Files whose names already satisfy the policy are not renamed.
3. The program does not silently invent a destination for an invalid result.

### REQ-003 — Preview without mutation

- **Status/source:** Accepted from the user request.
- Preview must be the default behavior.
- It must show each proposed source and destination name clearly.
- It must identify blocking conflicts before apply.
- It must provide totals for proposed, unchanged or skipped, conflicting, and invalid entries.
- Preview must not create, remove, rename, or modify any filesystem entry.

**Acceptance criteria**

1. Comparing the directory state before and after preview shows no changes.
2. Every proposed rename is visible in output before any apply operation is requested.
3. Conflicts produce visible diagnostics and a non-zero exit status when the plan is not safe to apply.

### REQ-004 — Require explicit apply

- **Status/source:** Accepted from the user request.
- Mutation must occur only when the user supplies the documented explicit apply command or option.
- Merely running preview, redirecting its output, or repeating preview must not authorize apply.
- Apply must calculate and validate a fresh plan from current filesystem state.
- Apply must not depend on an interactive interface.

**Acceptance criteria**

1. Omitting the apply argument never renames a file.
2. Providing the apply argument invokes fresh validation before mutation.
3. A folder changed between preview and apply is handled according to its current state, not the previous display.

### REQ-005 — Never overwrite an existing path

- **Status/source:** Accepted from the user request.
- A proposed destination is conflicting when:
  - a filesystem entry already exists at that path, including a path occupied by another planned source; or
  - two or more sources produce the same destination.
- The utility must not automatically number, delete, replace, or move a conflicting entry.
- A pre-apply conflict must block the entire apply before any changes begin.
- Apply must use a no-replacement operation for each destination; a check followed by a replacing rename is insufficient because another process could create the destination between those steps.
- For supported regular files in the same folder, the proposed implementation is to create the destination as a hard link using an exclusive standard-library operation and unlink the source only after link creation succeeds. If the filesystem does not support this safely, the item must fail without deleting the source.
- Source removal must never occur unless the corresponding destination was created successfully.

**Acceptance criteria**

1. If `clean-name.txt` exists, applying a plan that targets it leaves both the existing file and source file unchanged.
2. Duplicate destination proposals block apply before mutation.
3. A destination created concurrently during apply is not replaced.
4. Failure to create a destination leaves the source intact.
5. Tests verify destination contents and source preservation, not only emitted messages.

### REQ-006 — Report partial operational failure honestly

- **Status/source:** Proposed supporting behavior necessary for filesystem safety.
- Validation conflicts must block all changes before apply begins.
- Unexpected failures after mutation begins must stop further work unless continuing is demonstrably safer.
- The program must report which mappings completed and which did not.
- A partially completed run must return a non-zero exit status.
- A subsequent preview must reflect actual current names and allow remaining valid work to be retried without repeating completed changes.

**Acceptance criteria**

1. A simulated failure after one successful change produces a non-zero exit status and an accurate per-item report.
2. Successfully created destinations are not mislabeled as rolled back.
3. Retrying does not overwrite completed destinations or lose unprocessed sources.
