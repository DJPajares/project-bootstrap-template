Do not add a framework, third-party runtime dependency, network service, repository integration, task tracker, migration system, or speculative infrastructure. Preserve the current CLI flags and package layout.

## Recovery and failure behavior

“No overwrite” is the primary integrity invariant. A failed or conflicting rename must not remove or replace pre-existing destination content.

Preview is the normal preparation and recovery mechanism:

1. Preview the current filesystem state.
2. Resolve reported conflicts outside the utility if desired.
3. Apply using the existing CLI contract.
4. If apply is interrupted or reports an error, inspect its result and run preview again.
5. Treat the new preview as authoritative for the current filesystem state.

The utility need not provide transaction-wide rollback unless separately proposed and approved. Where multiple renames are processed, an execution error may leave earlier successful renames in place. Reporting must make this visible and must not describe the whole operation as successful. A rerun must re-evaluate current paths and retain all no-overwrite checks.

Recovery behavior must not depend on a journal, database, migration, network service, or newly introduced command-line flag.
