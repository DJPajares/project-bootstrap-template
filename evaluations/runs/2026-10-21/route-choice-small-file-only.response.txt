## Purpose and scope

People sometimes inherit a folder whose filenames contain inconsistent surrounding or repeated whitespace. Manually reviewing and renaming those files is tedious and error-prone, especially when a cleaned name already exists.

The utility will calculate a deterministic cleanup plan for regular files directly inside one selected folder. Preview is the default behavior. Renaming occurs only when the user explicitly requests apply mode.

- **First useful result:** A local command-line utility that previews old and proposed names, identifies conflicts, and safely applies an unchanged plan without overwriting any existing path.
- **Outside this version:** Recursion, directory renaming, symbolic-link processing, undo history, interactive prompts, graphical interfaces, servers, databases, external services, configuration files, plug-ins, background monitoring, and task-tracker integration.
- **Success evidence:** Representative filesystem tests show that preview makes no changes, apply performs only eligible renames, conflicts do not overwrite data, and failures produce truthful results and a non-zero exit status.
- **Tradeoff principles:** Prefer preventing data loss over completing every rename; prefer visible, deterministic behavior over broad cleanup; keep preview and apply behavior aligned; use only Python’s standard library.

## Proposed user workflow

1. The user supplies exactly one folder.
2. The utility inspects regular files immediately inside that folder; it does not recurse.
3. It calculates and prints a stable rename plan.
4. With no apply option, it exits without modifying the folder.
5. With the explicit apply option, it rechecks relevant filesystem conditions and attempts only safe renames.
6. It reports every applied, skipped, blocked, or failed item and returns an exit status reflecting the result.

A missing, inaccessible, or non-directory path is an error. An empty plan is a successful no-op.

## Filename cleanup policy

The following policy is recommended but remains a product decision to confirm before implementation:

- Operate on the complete basename, not on directory components.
- Remove leading and trailing Unicode whitespace.
- Replace every remaining run of one or more Unicode whitespace characters with one underscore (`_`).
- Preserve all other characters, including letter case and dots.
- Do not rename a file when the calculated name equals its current name.
- Reject a calculated name that is empty, `.` or `..`.
- Do not process directories or symbolic links.

This intentionally avoids transliteration, case normalization, punctuation removal, extension-specific rules, and platform-specific character rewriting.

## Safety and integrity

- The selected folder is the complete operation boundary.
- Every source and target must resolve to a direct child name within that folder; names must not introduce path separators or traversal.
- Existing targets are never removed, truncated, or replaced.
- Conflict checks include duplicate targets within the planned batch, not only paths present at initial inspection.
- Apply uses a no-overwrite mutation strategy. A check followed by an overwrite-capable rename is insufficient because another process may create the target between those actions.
- The recommended implementation direction for regular files is to create the target as a hard link using an operation that fails when the target already exists, then unlink the source. This stays within the standard library and same-folder filesystem boundary.
- If target creation succeeds but source removal fails, both names may reference the same file. The utility must report that recoverable duplicate state and must not delete either name automatically.
- If the environment cannot provide the required no-overwrite guarantee, apply must refuse the affected rename rather than weaken the contract.
- Concurrent modification by other processes is not prevented. It is detected where practical and reported; exclusive folder locking is outside this version.

## Structure and technical direction

The implementation is proposed as a small Python command-line package:

- `src/filename_cleanup/__init__.py` — package marker and version-independent package boundary.
- `src/filename_cleanup/cli.py` — argument parsing, user-facing output, and exit-code selection.
- `src/filename_cleanup/planning.py` — filename transformation, directory inspection, plan classification, and deterministic ordering.
- `src/filename_cleanup/apply.py` — revalidation and no-overwrite filesystem mutations.
- `tests/` — standard-library `unittest` coverage using temporary directories.
- `README.md` — supported Python version once selected, command examples, cleanup rules, safety behavior, and verified test command.

Responsibility boundaries:

- Planning is side-effect free after directory inspection and can be tested independently.
- Apply consumes a plan but must not trust it blindly; it revalidates sources and targets.
- The command layer does not implement filename or filesystem rules.
- No database, network access, account model, service process, or user interface is introduced.

Python 3 is accepted. The exact minimum supported Python version and executable/module name are open decisions to resolve before implementation. Until files exist, commands and paths above are proposed rather than verified.
