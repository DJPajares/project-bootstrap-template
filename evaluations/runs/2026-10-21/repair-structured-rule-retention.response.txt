## Purpose and scope

Revisioned Notes enables people to maintain private notes without losing work during concurrent editing or accidentally deleting notes through tag management.

The first useful result is a dependable note workflow in which:

- Notes are private to their owners.
- Only a note’s owner may edit it.
- Each accepted save creates or advances revisioned state.
- A conflicting save does not overwrite newer stored content or discard the user’s unsaved draft.
- Tags remain independent from notes, so deleting a tag never deletes an otherwise independent note.

This version does not add collaboration, public sharing, shared ownership, automatic conflict merging, offline synchronization, or a new release system. Those features require separate approval.

Success is demonstrated through focused runtime checks showing that authorized note operations succeed, unauthorized edits are rejected, conflicts preserve both authoritative content and the attempted draft, and tag deletion leaves notes intact.

When implementation choices compete, prefer data integrity, privacy, understandable recovery, and a small coherent change over convenience or speculative extensibility.

## Concepts, ownership, and invariants

### Note

A note is private, owner-controlled content with a stable identity and revision state.

- A note has exactly one authoritative owner.
- Visibility and edit authorization derive from authoritative ownership, not client-supplied claims.
- Only the owner may read or edit a private note unless a later approved requirement explicitly introduces another permission.
- An accepted content change advances the note’s revision.
- Revision identifiers are concurrency controls, not evidence that every historical revision must be exposed through a user interface.

### Draft

A draft is the content a user attempted to save.

- A submitted draft does not become authoritative until the save is accepted.
- If a revision conflict prevents a save, the attempted draft must remain recoverable and visible to the user.
- Preserving the draft does not authorize overwriting the current stored revision.
- Automatic merging is outside the current scope.

### Tag

A tag is an independently managed classification associated with zero or more notes.

- The note and tag have independent identities and lifecycles.
- Deleting a tag removes that tag and its associations.
- Deleting a tag never deletes an independent note or its content.
- Repeating deletion or encountering an already-absent association must not cause note deletion.

### Product invariants

- **INV-001 — Privacy:** A private note is available only within its owner’s authorized context.
- **INV-002 — Owner-only editing:** A non-owner cannot alter note content, revision state, ownership, or tags on the owner’s behalf.
- **INV-003 — Conflict safety:** A save based on a stale revision cannot silently overwrite the current revision.
- **INV-004 — Draft preservation:** A rejected conflicting save returns or retains the submitted draft in a form the user can recover.
- **INV-005 — Independent deletion:** Deleting a tag cannot delete any note.
- **INV-006 — Authoritative enforcement:** Permission and revision checks occur at the authoritative write boundary, not only in an interface.

## Primary workflows

### Create a note

1. An authenticated owner supplies the minimum supported note content.
2. The system creates a private note owned by that person with an initial revision.
3. The created note and revision become the authoritative stored state.
4. Failure must not report success or leave an ambiguously created note.

### Edit and save a note

1. The owner opens a note and receives its current content and revision identifier.
2. The owner submits an edited draft with the revision on which it was based.
3. The authoritative write boundary verifies ownership and compares revisions.
4. If ownership and revision are valid, the new content is accepted and the revision advances.
5. If authorization fails, no note state changes.
6. If the submitted revision is stale, no stored content is overwritten. The current stored revision and the unsaved submitted draft remain distinguishable so the user can recover or reconcile their work.

### Delete a tag

1. An authorized user requests deletion of a tag within their permitted context.
2. The tag and its associations are removed according to the established data model.
3. Every associated note remains present, private, and independently addressable.
4. A partial failure must not cascade into note deletion and must be reported without claiming complete success.

## Experience and quality constraints

- Conflict messaging must distinguish the current saved note from the unsaved attempted draft.
- Recovery must not require the user to reconstruct or retype a rejected draft.
- Permission errors must not disclose private content.
- Destructive actions must clearly identify whether they affect a note, a tag, or only an association.
- Loading, empty, denied, conflict, and failure states must preserve enough context for the user to understand the outcome.
- Interactive controls must use meaningful semantics, keyboard access, visible focus, and clear error identification where an interface exists.
- Focused tests must cover ownership, stale revisions, draft preservation, and tag deletion. No new end-to-end suite is required without authorization.
- Performance targets and supported deployment environments are not established by this document and must not be invented during implementation.

## Structure and technical direction

Preserve the existing project structure and technology choices. No repository implementation or technical stack was available for verification during this documentation-only refresh.

The implementation should maintain clear responsibility boundaries:

- The authoritative note domain owns note identity, ownership, content, and revision transitions.
- The authorization boundary verifies the acting identity against note ownership for every protected read or write.
- The persistence boundary performs revision comparison and content mutation atomically enough to prevent a stale save from overwriting a newer revision.
- The conflict result carries or durably preserves the attempted draft without treating it as authoritative note content.
- Tag management owns tags and note-tag associations but has no cascading authority over note records.
- Interface or transport code presents domain outcomes without replacing server-side permission or revision enforcement.

Exact paths, frameworks, storage mechanisms, migrations, and commands must be established from the repository before implementation. Any new technology remains a proposal until approved.

## Validation and delivery

Implementation evidence must include focused checks for:

1. An owner reading and saving their note against the current revision.
2. A non-owner being unable to read or edit the private note.
3. Two edits based on the same revision, with the first accepted and the second rejected as a conflict.
4. The rejected edit’s complete submitted draft remaining recoverable.
5. The current authoritative content remaining unchanged after the conflict.
6. Deleting a tag that is associated with one or more notes.
7. Every associated note remaining present and unchanged after tag deletion.
8. Relevant denied, repeated, and failure operations producing no destructive side effects.

Evidence must identify the artifact or revision tested, environment, date, coverage, result, and material gaps. Documentation review establishes consistency only; it is not runtime validation.

A sensible delivery sequence is:

1. Establish authoritative ownership and revision behavior.
2. Add conflict-safe saves with draft recovery.
3. Enforce independent tag deletion.
4. Verify the connected owner, conflict, and deletion workflows.

This sequence guides later planning but is not an executable task batch and does not authorize task creation or implementation.

## Decisions and uncertainty

### Accepted decisions

- Notes are private.
- Only owners may edit their notes.
- Saves use revision-aware conflict detection.
- A conflicting save preserves the unsaved draft.
- Tag deletion never deletes independent notes.
- Direct chat implementation requests do not require issue creation.
- Issue-backed work follows the Core / Notes tracker and repository-review workflow defined in `AGENTS.md`.

### Open implementation decisions

- The existing application stack, storage technology, schema, routes, components, and validation commands must be inspected before implementation.
- The exact draft-preservation mechanism is open. It may be client-held, returned by the conflict response, or durably stored if current architecture requires it. Whichever mechanism is selected must satisfy REQ-004 and REQ-007 without silently expanding product scope.
- The exact revision representation is open. It must support reliable stale-write detection and must not be accepted solely on client authority.
- Error shapes and interface presentation are open within the privacy, clarity, and recovery requirements above.

These decisions block detailed implementation design, not the approved product behavior. The project owner approves consequential changes to scope, architecture, privacy, or data lifecycle.
