````markdown
# Filename Cleanup Preview — Project Requirements Document

**Status:** Draft project contract; user-supplied constraints are accepted, while the cleanup transformation policy remains proposed pending approval.
**Owner:** Project owner
**Updated:** 2026-10-21
**Approval source:** The project constraints were supplied directly by the project owner. Proposed cleanup rules require approval before implementation.

This document owns product direction, scope, behavior, and decisions. `AGENTS.md` owns execution rules. An authorized chat request owns work status until another task system is explicitly selected. Validation reports attached to a change own observed evidence. Intended behavior, implementation status, validation, and approval are distinct.

## Purpose and scope

Filename Cleanup Preview is a small command-line utility for people who want to clean up filenames in one local folder without risking an unexpected bulk rename.

The first version should make the proposed changes visible before touching the filesystem. Applying those changes must require a separate, explicit command. The utility should be conservative: ambiguous or unsafe changes are reported and skipped rather than guessed.

- **First useful result:** A Python standard-library command that scans one explicitly selected folder, prints a deterministic rename plan, and performs exactly that plan only after an explicit apply request.
- **Outside this version:** A graphical interface, server, database, external service, task-system integration, recursive traversal, background monitoring, content modification, directory renaming, undo history, automatic conflict resolution, and cross-folder moves.
- **Success evidence:** Representative temporary-folder tests show accurate previews, no mutation during preview, explicit application, protection against overwrites and collisions, and useful failure reporting.
- **Tradeoff principles:** Prefer safety over renaming more files; keep preview and apply behavior consistent; avoid hidden filesystem effects; use only the Python standard library.

## Concepts and invariants

- A **target folder** is the single directory explicitly supplied by the user.
- A **candidate file** is a direct child of that folder that is a regular file. Subdirectories and their contents are not candidates.
- A **cleanup policy** is the deterministic transformation from a current filename to a proposed filename.
- A **rename plan** records each original path, proposed path, and whether the change is safe, unchanged, or blocked.
- A **conflict** exists when multiple source files resolve to the same destination or a destination is occupied by a path that is not safely moved as part of the same plan.

The following invariants apply:

1. Preview mode never changes the filesystem.
2. Apply mode is entered only through an explicit apply option; omission of that option always means preview.
3. The utility never overwrites an existing file or directory.
4. Only direct regular-file children of the selected folder are eligible.
5. The filename extension and file contents remain unchanged unless a later approved requirement explicitly says otherwise.
6. A blocked or invalid plan produces no partial batch of renames.
7. Re-running preview against an unchanged folder produces the same plan and ordering.
8. Applying a plan successfully leaves a subsequent preview with no remaining changes under the same cleanup policy.

## Proposed cleanup policy

The exact meaning of “cleanup” is the only material product decision still open. The recommended first policy is deliberately narrow:

1. Operate on the filename stem while preserving the final extension exactly.
2. Remove leading and trailing whitespace from the stem.
3. Replace each internal run of whitespace with a single hyphen.
4. Leave letter case, punctuation other than whitespace, Unicode characters, and dotfiles unchanged.
5. Skip a result that would be empty, `.` or `..`, identical to the original name, or invalid on the current platform.
6. Do not transliterate Unicode, strip accents, renumber duplicates, or append conflict suffixes.

Examples under this proposal:

| Current name | Proposed name |
| --- | --- |
| `  trip photo  .jpg` | `trip-photo.jpg` |
| `Quarterly   Notes.txt` | `Quarterly-Notes.txt` |
| `résumé  final.pdf` | `résumé-final.pdf` |
| `already-clean.txt` | unchanged |
| `.gitignore` | unchanged |

Approval of this policy is required before implementation because a different policy would change filenames and test expectations. It does not block preparation of the project foundation.

## Structure and approach

The proposed implementation remains intentionally small:

```text
filename-cleanup-preview/
├── PRD.md
├── AGENTS.md
├── CLAUDE.md
├── README.md
├── filename_cleanup.py
└── tests/
    └── test_filename_cleanup.py
```

- `filename_cleanup.py` will contain argument parsing, candidate discovery, the pure cleanup transformation, plan construction, conflict validation, reporting, and guarded application.
- `tests/test_filename_cleanup.py` will use `unittest`, `tempfile`, and filesystem snapshots to verify behavior.
- `README.md` will contain supported Python versions, invocation examples, exit codes, the approved cleanup rules, and platform limitations.
- `PRD.md` remains the authority for product behavior.
- `AGENTS.md` remains the authority for implementation and delivery discipline.
- `CLAUDE.md` provides the one-way Claude bridge to `AGENTS.md`.

The implementation should separate pure plan construction from filesystem mutation. Apply must consume a freshly validated plan rather than interpret terminal output or rely on a previously saved plan.

Python version support is not yet accepted. The recommendation is one currently maintained Python 3 version available in the eventual target environment, with the exact minimum recorded in `README.md` before implementation.

No command has been implemented or executed. The following are proposed verification commands once the files exist:

```bash
python -m unittest discover -s tests -v
python -m compileall filename_cleanup.py tests
```

## Validation and delivery

Implementation acceptance requires evidence from isolated temporary directories; tests must never rename uncontrolled user files.

Required scenarios include:

- Empty folder and folder with no applicable changes.
- A single safe rename and several independent safe renames.
- Preview followed by a filesystem snapshot proving no mutation.
- Apply followed by content and filename verification.
- Existing destination conflicts.
- Two or more sources mapping to one destination.
- Files whose names differ only by filesystem case behavior.
- Nested directories and symbolic links, which remain untouched.
- Rename swaps or cycles if REQ-006 is approved.
- A failure during application and restoration to the original state.
- A second preview after successful apply reporting no changes.
- Invalid, missing, and inaccessible target paths.

Evidence must name the code revision or artifact, Python version, operating system/filesystem, date, scenarios covered, results, and gaps. Documentation review alone is not runtime validation.

A sensible delivery sequence is:

1. Approve the cleanup policy, supported Python baseline, symlink treatment, and conservative all-or-nothing behavior.
2. Implement deterministic discovery, transformation, plan validation, and preview output.
3. Add explicit application with collision-safe execution and recovery.
4. Validate the complete behavior and document actual commands and limitations.

These are outcome slices for later planning, not executable tasks and not authorization to implement them.

## Decisions and uncertainty

### Accepted decisions

- The deliverable will be a small Python utility.
- Runtime dependencies are limited to the Python standard library.
- It operates on one folder.
- Preview precedes mutation, and mutation requires explicit apply.
- Existing files must never be overwritten.
- There is no graphical interface, server, database, external service, or tracker.
- This bootstrap prepares project documents only; it does not implement the utility.

### Proposed decisions

- Preview is the default and `--apply` is the explicit mutation option.
- Traversal is non-recursive.
- Only direct regular files are eligible; symbolic links are not followed or renamed.
- Any conflict blocks the entire apply operation.
- The recommended narrow cleanup policy is used.
- A collision-safe temporary-name sequence supports valid rename cycles.
- Tests use only `unittest`, `tempfile`, and other standard-library modules.

### Open gates

- **Cleanup transformation:** The project owner must approve or replace the proposed policy before implementation. This blocks transformation code and its expected results.
- **Python baseline:** Select the minimum supported Python version from the actual target environment before implementation. This affects syntax and compatibility checks.
- **Platform scope:** The recommendation is to support the platform used for initial development and treat broader Windows/macOS/Linux compatibility as unverified until tested. Claiming cross-platform support is blocked pending evidence.
- **Apply recovery:** The recommended cycle-safe, rollback-capable batch behavior should be approved with REQ-005 and REQ-006. A simpler refusal of cycles is also safe but less capable.
````

````markdown
- Language: Python 3.
- Runtime dependencies: Python standard library only.
- Project type: a small command-line utility, not a service or package ecosystem.

```

Do not add third-party packages, packaging infrastructure, continuous delivery, or release tooling without an accepted need.

## Architecture Principles

- Keep cleanup transformation and plan construction pure and independently testable.
- Treat the target folder as an explicit boundary; do not recurse or follow paths outside it.
- Build one complete plan before mutation. Validate every destination and relationship before the first rename.
- Preview and apply must use the same discovery, transformation, and validation logic.
- Apply must recompute the plan from current filesystem state rather than trust stale displayed output.
- An unsafe or conflicting plan must leave the folder unchanged.
- Existing destinations are authoritative filesystem facts. Never overwrite them or assume permission from a proposed name.
- Preserve independent plan states: unchanged, safe rename, blocked, and invalid are not interchangeable.
- If rename cycles are approved, use collision-proof temporary paths and attempt restoration after a mid-operation failure.
- Never report full success after a partial failure. Report the paths restored, paths still displaced, and required manual recovery.
- Treat filesystem case sensitivity and platform filename restrictions as observed environment behavior, not universal assumptions.
- Symbolic links and directories are outside the first version unless the PRD is explicitly amended.
````
