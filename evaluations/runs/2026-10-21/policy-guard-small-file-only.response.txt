**Status:** Draft; user-supplied scope and constraints are accepted, while the cleanup transformation policy remains proposed pending approval  
**Owner:** Project owner  
**Updated:** 2026-10-21  
**Approval source:** User request dated 2026-10-21

## Purpose and scope

Filename Cleanup Preview is a small command-line utility for people who need to clean filenames in one local folder without risking an immediate or destructive bulk rename.

Its defining behavior is a two-step workflow: preview a complete rename plan first, then perform those same safe changes only after an explicit apply request.

- **First useful result:** A Python standard-library utility that examines one specified folder, presents proposed filename changes without modifying files by default, and applies safe renames only when explicitly requested.
- **Outside this version:** Graphical or web interfaces, servers, databases, external services, task-system integration, recursive traversal, background monitoring, content modification, directory renaming, automatic conflict resolution, undo history, and cross-device file moves.
- **Success evidence:** Representative folder scenarios demonstrate accurate previews, no preview-time mutations, refusal to overwrite or produce ambiguous destinations, and successful application of a conflict-free plan.
- **Tradeoff principles:** Prefer safety and understandable output over aggressive cleanup. Refuse ambiguous work rather than guessing. Keep the utility dependency-free and small enough to inspect locally.

## Primary workflow

1. The user invokes the utility for one existing folder.
2. The utility inspects the files directly inside that folder; it does not recurse.
3. It computes and displays the source and proposed destination for every filename that would change.
4. Preview is the default and never renames anything.
5. The utility reports conflicts and invalid operations before application.
6. Only an explicit apply option authorizes renaming.
7. Apply revalidates the plan against the current folder state before the first rename.
8. If validation fails, no rename begins and the utility reports the reason.
9. If validation succeeds, the utility performs the planned renames and reports the result.

## Proposed filename policy

The first implementation should adopt a deliberately conservative policy:

- Operate on the filename stem while preserving the final extension exactly.
- Trim leading and trailing whitespace from the stem.
- Replace each run of whitespace in the stem with one hyphen.
- Leave letter case, punctuation other than whitespace, Unicode characters, and extension spelling unchanged.
- Leave a filename unchanged when the policy produces the original name.
- Reject a proposal that would produce an empty stem, `.` or `..`, a path separator, or another name invalid on the active platform.
- Treat dotfiles without another suffix, such as `.env`, as extensionless names and leave them unchanged unless a later approved policy explicitly covers them.
- Do not append numeric suffixes to resolve conflicts.

This policy is a proposal, not yet an approved product decision. Its approval blocks implementation of the transformation itself; preview, safety, and test structure can still be discussed without inventing another policy.

Examples under the proposed policy:

| Current filename | Proposed filename |
| --- | --- |
| ` quarterly  report .pdf` | `quarterly-report.pdf` |
| `team   notes.txt` | `team-notes.txt` |
| `Photo.JPG` | `Photo.JPG` |
| `.env` | `.env` |

## Structure and technical direction

This is a single-package Python command-line utility with no network behavior or persistent application state.

Proposed minimal layout:

- `src/filename_cleanup/` — implementation package.
  - `cli.py` — argument parsing, exit codes, and user-facing output.
  - `planning.py` — deterministic filename transformation, plan construction, and conflict validation.
  - `apply.py` — final revalidation and safe rename execution.
- `tests/` — standard-library `unittest` coverage using temporary directories.
- `README.md` — installation-free invocation, preview/apply examples, cleanup policy, and safety limitations.
- `PRD.md` — approved product direction and requirements.
- `AGENTS.md` — execution and validation rules.
- `CLAUDE.md` — bridge to the canonical agent rules.

Accepted technical constraints:

- Python standard library only.
- Local filesystem access only.
- No interface beyond the command line.
- No server, database, external service, telemetry, or tracker.
- No application implementation is included in this bootstrap.

Proposed command shape for later implementation:

- Preview: `python -m filename_cleanup FOLDER`
- Apply: `python -m filename_cleanup FOLDER --apply`

These commands are design proposals and have not been implemented or executed.

## Safety and integrity

- Preview has no filesystem write permission by product design.
- Apply authority comes only from the explicit apply option for the specified invocation and folder.
- Every destination must be checked immediately before application.
- Existing entries must never be replaced, including through platform-specific rename behavior.
- Symlink behavior must be resolved before implementation. The recommendation is to exclude symlinks from the first version because their target and platform semantics increase risk.
- The plan must use filesystem paths internally without constructing commands for a shell.
- Temporary names, if required for safe ordering, must remain within the selected folder, be unique, and never replace an existing entry.
- File contents, metadata beyond unavoidable rename effects, and entries outside the selected folder are out of scope.
- A preview is evidence of intent, not a durable authorization token. Apply recomputes and revalidates against current state.

## Validation and delivery

Required evidence for implementation acceptance:

- Unit tests for the approved filename transformation.
- Temporary-directory tests for preview immutability.
- Tests for existing-destination conflicts and internal plan collisions.
- Tests confirming directories and nested files are ignored.
- Tests for unchanged names and empty plans.
- Tests for explicit apply behavior and preserved file contents.
- Tests for rename chains or swaps if the chosen plan permits them.
- Tests for validation failure before mutation.
- Runtime checks of preview and apply in disposable temporary folders.
- Documentation review for consistent commands, scope, and safety claims.

Evidence must record the artifact or revision, environment, date, checks performed, results, and material gaps. Document review alone is not runtime validation.

Indicative delivery sequence:

1. Approve the filename policy and symlink boundary.
2. Implement deterministic planning and preview with focused tests.
3. Implement full-plan validation and explicit apply.
4. Exercise conflicts, overlapping renames, and failure reporting.
5. Complete usage and safety documentation.
6. Stop for human review; do not publish or distribute without separate authorization.

This sequence describes outcomes, not executable tasks or permission to create them.

## Decisions and uncertainty

### Accepted

- The project is a small Python standard-library utility.
- It works on one folder.
- Preview precedes any rename and is the default behavior.
- Renaming requires explicit apply.
- Existing files must never be overwritten.
- There is no graphical interface, server, database, external service, or tracker.
- This bootstrap supplies project documents only, not the program.

### Proposed decisions requiring owner approval

- **Cleanup transformation:** Use the conservative whitespace-only policy defined above. This blocks transformation implementation.
- **Traversal:** Inspect only immediate regular files, not nested folders. This affects scope and tests.
- **Symlinks:** Exclude symlinks. This affects eligibility and platform behavior.
- **Apply semantics:** Validate the complete plan before the first rename and reject the complete plan on any known conflict. This affects safety and recovery behavior.
- **Command form:** Default preview with a single `--apply` option. This affects CLI documentation and tests.

### Material risks

- Filesystem state may change between inspection and rename. Revalidation reduces but cannot eliminate all races; implementation must report observed partial outcomes truthfully.
- Case-only renames and case-insensitive filesystems have platform-specific behavior. The first implementation should detect uncertainty and refuse unsafe cases unless focused tests establish supported behavior.
- A cleanup rule that is too aggressive can reduce filename meaning. The proposed policy intentionally limits normalization to whitespace.
